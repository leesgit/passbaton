# PB154-M1 — 전체 카드 vs loop 최소 카드 (Node 비교 · 2026-10-23)

> 계약: Astra reply-154 §2 PB154-M1 · §3(측정 고정표) · §4 M0·M1 행.
> 이 문서는 **같은 고정 입력에서 카드 출력이 어떻게 다른가**만 말한다. 랄프 작업 정확도·비용 효과는 **미측정**이다(전향 시험 전 미결).

## 2. 결과 — 카드만 (`buildResumeCard`, 3200 자 예산)

| 변형 | 전체 카드 자/줄 | 최소 카드 자/줄 | 본문 뺀 원천 | 빌드 중앙값 ms 전체/최소 |
|---|---|---|---|---|
| as-is (DEMO_STOP 없음) | 3,160 / 41 | 2,675 / 24 | fix_plan · HANDOFF | 7.94 / 4.74 |
| DEMO_STOP 생김 | 3,180 / 43 | 2,713 / 27 | fix_plan · HANDOFF | 8.54 / 5.05 |
| 작업 절 소실(no_block) | 3,142 / 39 | 2,769 / 25 | HANDOFF (fix_plan 은 NOT READ 줄) | 6.68 / 4.68 |
| 활성 처분 행 추가 | 3,191 / 41 | 2,746 / 25 | fix_plan · HANDOFF | 7.54 / 4.65 |

정보 보존(네 변형 모두 참):

- 정지 원천 상태 동일(없음 = `NOT READ (file not found)` · 생기면 사유 본문이 최소 카드에 그대로)
- 현재 작업 상태·첫 줄 동일 — 작업 절 소실 시 두 카드 모두 첫 줄 `⚠ CURRENT TASK UNKNOWN — block "지금 할 일" not found …`
- 전체 카드에 보인 처분 색인 행은 최소 카드에 전부 있다 — **전체 카드는 활성 처분 데이터 행 12 개 중 4 개만**(머리 행 포함 5 줄 · 잘림 · 줄 15 까지), 최소 카드는 **12 개 전부**(블록 8-24 잘림 없음 · 뺀 본문의 몫이 2.7.2 재분배로 색인에 간다)
- 읽힌 모든 원천의 `경로:범위` 와 `sha1` 이 최소 카드에도 있다(원천 검사를 생략하지 않았다 — 같은 해시)
- 못 읽은 원천의 `NOT READ` 줄 동일
- 변형이 최소 카드에서 보인다: DEMO_STOP 사유 ✔ · 작업 절 소실 경고 ✔ · 맨 앞에 끼운 활성 처분 행 ✔

⚠ 해석: 최소 카드가 **짧아진 폭은 작다**(−385 ~ −485 자). 빠진 fix_plan·HANDOFF 발췌 대신 색인 본문이 늘었기 때문이다. 같은 예산 안에서 「랄프가 PROMPT 로 이미 읽는 원천의 중복 발췌」 를 「PROMPT 가 읽으라고 하지 않는 처분 색인」 으로 바꾼 것이다(packet-154 §1-3 의 순증 정보).
빌드 시간 차(≈ 3 ms)는 전체 카드의 재분배 추가 읽기 때문이다 — 최소 카드도 원천 넷을 모두 읽는다.

DB 사본에 `run_origin` 칸이 없어(2.7.2 DB) unknown 실행의 Recent 는 거르지 않고 전부 `[origin unknown]` 으로 나온다 — B 의 효과(대화 카드에서 loop 행 제외)는 2.7.3 이 Stop 을 몇 번 쓴 뒤에야 실물에서 보인다.

## 4. 역검증(§4 M0·M1 행)

- 사본 해시 하나 변경(`INDEX.md` 끝에 공백 1 바이트) → `INVALID — fixture hash mismatch (비교 무효)` · exit 3 · 결과 미출력 ✔
- 실행 도중 사본이 바뀌면 끝 대조에서 `INVALID — fixture changed during the run` (변형은 임시 복사본에만 적용)
- 토큰 필드: 이 비교는 Node 출력만 보므로 토큰 원값이 **없다** → 토큰·비용 칸은 「미측정」 이다(문자 수로 환산하지 않음)
- 이벤트 종류: startup 만 쟀다. resume·compact 는 미측정(섞지 않음)

## 5. 미결·한계

- 랄프가 최소 카드에서 같은 항목·정지 판단·필수 Read 를 하는지는 **미측정**(아래 전향 시험)
- 제안 role 설정은 Ashfall 레포에 아직 없다 — 대화 세션이 적용 여부를 정한다
- 실제 토큰(입력·캐시 읽기·캐시 쓰기·출력) 미측정

## 7. 전향 시험 사전 명세 — 초안 (reply-154 §3 고정표)

> 실행 조건: **N153 종료 뒤 자연스러운 블록 경계**의 격리 사본에서만. 생산 랄프를 두 번 돌려 같은 일을 구현시키지 않는다.
> 비교는 **전체 카드 대 최소 카드**만(전체 훅 끄기는 Stop 등 다른 동작까지 바꾸므로 하지 않는다). 두 호출은 탐색 결과이며 일반적 효능 입증이 아니다.

| 고정할 것 | 이번 초안의 값(측정 전에 채워 잠근다) | 비교·해석 |
|---|---|---|
| 소스·설치본 버전 | 2.7.3 후보 tarball 해시(Z 단계) · 격리 설치 경로 · 두 세션 같은 설치본 | 다르면 쌍 무효 |
| PROMPT·fix_plan·HANDOFF·INDEX·DB 사본 해시 | 블록 경계 시점 사본 sha256 다섯(위 §1 형식) · 두 세션 같은 사본에서 출발 | 시험 도중 바뀌면 그 쌍 무효 |
| 모델·effort·도구 권한·시작 조건 | `ralph_loop.sh` `build_claude_command` 와 같은 `--model --effort --allowedTools` · 새 세션(startup) · `--resume` 없음 | 다른 조건을 카드 효과로 보지 않음 |
| 시험 과제 | 「매 루프 1~2 단계만: 원천을 읽고 다음 항목을 고르고 정지 여부를 판정하라 — 구현하지 마라」(같은 문장) | 다른 난이도를 카드 효과로 보지 않음 |
| 정답 항목 ID · 대기/중단 여부 · 필수 원천 | 카드가 아닌 **고정된 정본**(사본의 fix_plan `## 지금 할 일` · DEMO_STOP · INDEX 활성 처분)에서 시험 전에 적는다 | 출력에서 기대값을 만들지 않음 |
| 순서 | 사전에 정한다(예: 최소 → 전체) · 두 세션 독립(같은 DB 를 공유하지 않음) | 순서 효과는 해석에 적는다 |
| 카드 전문·문자 수·가능하면 실제 토큰 수 | transcript `hook_success` 전문 · 문자 수 · 결과 JSON 의 토큰 | 문자 수를 토큰으로 환산하지 않음 |
| 입력·캐시 읽기·캐시 쓰기·출력 토큰 원값 | result JSON `usage` 네 칸 원값 | 입력만 줄었다고 총비용 감소로 판정하지 않음 · 칸이 빠지면 「미측정」 |
| 첫 Read 까지 시간·Read 범위·선택 항목·중복 작업 | transcript 시각 · Read 의 path/offset/limit · 고른 항목 ID · 이미 끝난 일 재수행 여부 | 속도와 정확도를 별도 기록 |

**적용 조건(전부 참이어야):** 동일 사본에서 필수 정보 보존(§2 항목) · 두 세션 모두 올바른 항목·정지 판단·필수 Read 수행 · 최소 카드의 실제 주입량 감소. 하나라도 틀리면 적용 보류.
만족해도 결론은 「관찰한 과제에서 전체 본문의 추가 이득 미관찰, 최소 카드로 줄일 근거 확보」 까지다 — 「passbaton 은 랄프에 도움 안 됨」 으로 확대하지 않는다(처분 색인이라는 순증 정보가 남는다).

**무효·멈춤:** 사본 해시 불일치 · 모델/권한 차이 · 이벤트 종류 혼합(startup 외) · 토큰 칸 누락 → 그 쌍은 비교 무효/미측정. 같은 접근 재시도는 근거 있는 수정 뒤 1 회까지.
